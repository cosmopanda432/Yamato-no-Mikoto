## 0. 位置づけ

eli3 光明想 pilot の結果は **HALT-only: pass@1 −13.66pp / undef-symbol 0%** — 遮断側
(千人死) だけが建ち、生成回復側が無い状態。原典の要請は Pattern 3.4:

> 「愛我那邇妹命、汝爲然者、吾一日立**千五百產屋**」 (上-2)

遮断の損失 (一日千人死) を上回る回復機構 (一日千五百產屋) があって初めて収支が
純増になる。本書はその**產屋側の実装残項目**を、コード事実と古事記 anchor 付きで
実装可能な粒度に落としたもの。

## 1. 現状のコード事実 (2026-07-03 確認)

| 事実 | 場所 |
|---|---|
| `Verdict.REPAIR` は enum として定義済み | `yomotsu_hirasaka.py:30` |
| evaluator は中間 v_score (0.3 ≤ v < 0.7) で REPAIR を実際に返す | `elixir_evaluator.py:183-188` |
| decode loop が分岐するのは **HALT のみ**。REPAIR は StepLog に記録されるだけで COMMIT と同挙動 | `firewall_decoder.py:227` |
| evaluator は診断情報 (どの bad pattern / bracket / do-end / 光明想失敗種別) を計算した上で**破棄**。`L5ToL3Verdict` が運べるのは `{verdict, v_score}` のみ | `elixir_evaluator.py:113-150` |
| 実 subprocess 評価 (undef-symbol 検出可能) は生成完了後の別経路 | `scripts/eval/elixir_eval.py` |

**結論**: REPAIR は protocol の語彙としては存在するが、end-to-end で no-op。
「直せ」は言えるが「何を直すか」を伝える経路が無く、受け手も居ない。

なおこれは Firewall の設計が正しく働いている証拠でもある — 事戸 (Pattern 3.3) が
狭いから ad-hoc な診断漏洩ができず、REPAIR には明示的な schema 拡張が必要になる。

## 2. 残項目 (実装ブロッカー 5 件)

### 項目 A: 葦船 log — 棄却 sample の系統的保全

- **anchor**: Pattern 2.2 「此子者入葦船而流去…是亦**不入子之例**」—
  失敗作は消さずに流す。ただし成功集合 (子之例) には数えない。
- **内容**: HALT / REPAIR / post-hoc fail した生成物を理由コード付き JSONL に永続化。
  現状 `FirewallResult` は `halted_early` flag と `steps` を持つが揮発する。
- **スキーマ案**: `{prompt_id, arm, seed, attempt_idx, verdict, v_score, reason_code,
  halted_at_step, generated_text, ts}` — 成功出力とは**別ファイル** (不入子之例)。
- **設計制約**: 既存 arm の生成 byte に影響を与えない (書き出しは decode loop 外)。
- **DoD**: smoke run で棄却全件が理由コード付きで残る。失敗 mode 分布が集計可能。
- **規模**: S。**着手点** — 処方 (項目 D) の選定は失敗分布の観測 (卜相) が前提。

### 項目 B: 事戸 protocol 拡張 — 診断 field

- **anchor**: Pattern 3.3 事戸は定型。拡張は `prompt_len` (eli3) と同じく
  **明示的 schema 変更**として行う。
- **内容**: `L5ToL3Verdict` に `reason_code: ReasonCode` (enum) と
  `hint: str` (上限長付き、default "") を追加。
  - `ReasonCode` 案: `NONE / TRACE_MISSING / TRACE_INSUFFICIENT / BRACKET_MISMATCH /
    DO_END_MISMATCH / BAD_PATTERN / LOW_SCORE / UNDEF_SYMBOL`
  - evaluator が既に計算している診断を、破棄せず code に落とすだけ
- **設計制約**: Firewall 原則は不変 — tensor / hidden state / 評価器内部統計は
  引き続き通さない。`hint` は `__post_init__` で型 + 長さ validation
  (既存の防御スタイルに合わせる)。
- **DoD**: 既存テスト green。eli2 非改変。診断なし時は従来と同値
  (`NONE`, `""`) で後方互換。
- **規模**: S。

### 項目 C: 還降 loop — L3 側 REPAIR ハンドラ + 再試行 policy

- **anchor**:
  - 還降 (Pattern 2.1 v0.2): 「亦**還降**改言」— 出力済み prefix の遡及編集は不可、
    修正は**先頭からの再生成のみ**
  - 如先 (同): 「更往廻其天之御柱**如先**」— 再試行で変えるのは指示された最小変更
    (hint) のみ、他の全変数は固定
  - 水蛭子後の再試行成功 (Pattern 2.3): **HALT した sample も retry 対象**。
    水蛭子 (失敗) → 卜相 (診断) → 改言 (hint) → 再降臨 (再生成) → 成功、が原典の loop
- **内容**:
  1. decode 中の REPAIR verdict は**即中断しない** (中間帯 = まだ COMMIT に化け得る)。
     完走後の final_verdict と post-hoc eval 結果で retry を trigger する
  2. retry は prompt 先頭から再生成。診断 hint の注入以外、条件は完全固定
  3. retry budget (`max_attempts`) を `FirewallConfig` 相当に追加
- **seed 派生の統制条件**: attempt 0 の seed は既存派生式 (`args.seed * P + i`) と
  **同値**であること — これにより repair arm の attempt 0 が既存 arm と
  byte-identical になり、ablation の統制が成立する (修正 D の系譜)。
  retry (attempt r ≥ 1) は既存 seed 空間と衝突しない派生
  (例: `base + (r) * K`、K は prompt 数 × arm 数より十分大きい定数) で行う。
- **DoD**: repair arm の attempt 0 が firewall arm と byte-identical (検証 script pass)。
  smoke で retry 発火と budget 遵守を確認。
- **規模**: M。項目 B に依存。

### 項目 D: 処方 — symbol-level did_you_mean hint 注入

- **anchor**: Pattern 2.3 卜相 — 外部評価器が原因を特定し、生成側は
  **指示された最小修正のみ**加えて再試行する。
- **教訓 (memory `project-mechanical-repair-mbpp-go-zero`)**: 構文レベル一括整形
  (`goimports` 0/374、`Code.format_string!` 構造的ゼロ) は禁止経路。
  認可された再導入路は **symbol レベル (did_you_mean 型 hint) のみ**。
- **2 段構成と優先順位**:
  | 段 | 診断源 | 出せる hint | 優先 |
  |---|---|---|---|
  | decode 中 (hot path) | heuristic evaluator | bracket / do-end / trace 不足 | 後 |
  | **post-hoc** | `elixir_eval.py` subprocess | **undef-symbol + did_you_mean 候補** | **先** |
  post-hoc を先に建てる。undef-symbol は −13.66pp の主因 (光明想が守った軸) であり、
  効果実証があるのは symbol レベルのみ。
- **内容**: post-hoc fail 時、エラーから undef symbol を抽出し、
  retry prompt に hint (例: `# hint: Enum.fitler は未定義。Enum.filter か`) を注入。
  HALT (trace 系) の retry には trace pre-seed 強化を hint とする。
- **設計制約**: hint 注入以外の prompt 差分ゼロ (如先)。hint は L5→L3 の
  `hint` field 経由 (項目 B) — 別途の side channel を作らない。
- **DoD**: undef-symbol fail に対し hint 付き retry が走り、hint 以外の
  prompt diff がゼロであることをテストで担保。
- **規模**: M。項目 C に依存。処方の重み付けは項目 A の失敗分布を参照。

### 項目 E: 収支 judge — 千/千五百 metric

- **anchor**: Pattern 3.4 — 勝利条件は「產屋 ≥ 死者 + 500」つまり**純増**。
- **内容**: `judge_win_condition_elixir.py` に repair mode を追加
  (先例: koumyou-on 追加、commit `2f0659e`)。出力すべき収支:
  - Δpass@1 (vs firewall-off baseline / vs HALT-only)
  - undef-symbol 率 (HALT-only の 0% 近傍を維持できているか)
  - 平均 attempt 数 (計算コスト = 產屋の建設費)
- **win condition 案**: undef 率 ≤ HALT-only + ε かつ pass@1 gap (−13.66pp) の
  有意な回収、attempt budget 内で。
- **第 4 指標 (2026-07-03 追記、不浄観 audit)**: 乖離率
  `hack_gap = P(subprocess fail | v_score ≥ commit_threshold)` — proxy (v_score) が
  COMMIT と言ったのに大地 (subprocess) が否定した率。v_score の keyword scoring は
  stuffing 可能な gameable proxy であり (検証済み)、この指標が proxy 健全性の監視役。
  詳細: [`docs/memo/2026-07-03_須弥山報酬ハック原理.md`](../../../docs/memo/2026-07-03_須弥山報酬ハック原理.md) §7-8
- **DoD**: `--mode repair-on` が上記 4 指標を出力し勝敗判定を返す。
- **規模**: S。項目 C/D の arm が存在して初めて意味を持つ。

## 3. 依存関係と着手順

```
A 葦船 log (独立) ──────────┐
B 事戸拡張 (独立) → C 還降 loop → D 処方 (A の分布を参照) → E 収支 judge
```

**推奨順: A → B → C → D → E** — 卜相 (失敗の観測) なしに改言 (処方) はできない。
