## 結論

### 達成

1. **Firewall の構造的隔離性質**は humaneval-elixir 3 seed で実測確認 → 本プロジェクト
   の一次基準達成 ([[project-firewall-purpose]] が言う L3↔L5 隔離壁)
2. **FirewallDecoder の修正 H (token-level stop_token early-stop)** が 2 dataset で
   一貫した +~2.5pp pass@1 uplift を生む systematic な効果と確認

### 未達

3. **Win Condition Δ ≥ +5pp は両 dataset で未達** (humaneval +2.28pp、mbpp +2.52pp)。
   3 seed CI は重なり、1 seed は CI なし。+5pp 閾値は Go 版 full mode 想定で、
   kotodama 撤去後の本構成にはそもそも適合しない可能性 → 閾値再設計の議論余地

### 興味深い発見

4. **compile uplift の dataset 依存性**: humaneval ±0 vs mbpp +2.77pp。仮説は
   「humaneval は元から compile が難しく天井効果、mbpp は over-generation による
   compile 失敗の余地が残り early-stop が直接効く」
5. **undef は両 dataset で減少方向**だが、絶対値は dataset の base rate に依存
   (humaneval -2.28pp / mbpp -0.25pp)。型ハルシ surface area の構造的差異

## 次の論点 (持ち越し)

1. **Win Condition 閾値の再設計**: 固定 +5pp は dataset の base rate を無視している。
   高 base rate dataset (mbpp の 86.90% compile 等) では構造的に +5pp が困難。
   閾値を `max(base_rate, 1 - base_rate)` でスケールする等の改良案
2. **n=3 seed の検出力不足**: SE が大きく Δ +2.5pp が偶然か判定困難。systematic
   性 (2 dataset で一貫) は定性的証拠だが、検出力を出すには n=10 程度が望ましい
3. **mechanical_repair の Elixir-native 再設計**: `Code.string_to_quoted/2` の
   error から `did you mean ...` hint 抽出して symbol typo を矯正する prototype。
   humaneval-elixir undef 2.90% / mbpp 1.76% の残量が攻撃対象
4. **timeout_rate 0.62% (humaneval yamato 1/161 × 3 seed すべて)**: 構造的に
   同じ問題が 3 seed で timeout している → 1 問特定して原因調査の価値あり
