# 須弥山に隠された AI 報酬設計原理 / 手抜き対策原理

仏教宇宙論 (須弥山・六道・三界・地獄説) から抽出した、AI への報酬設計および怠惰 (手抜き) 対策の設計原理。本プロジェクト Yamato-no-Mikoto は既に Yomi (黄泉比良坂)・Kotodama・Tsukuyomi など日本神話/仏教語彙を中核 metaphor として採用しているため、須弥山系の原理を自然に拡張可能。

本文書は **設計示唆の覚書** であり、実装は未着手。

---

## Part 1: 須弥山構造に隠された 5 つの報酬設計原理

### 1. 三界の階層 = 報酬の質的多層性 (スカラー報酬の否定)

欲界・色界・無色界。下から上へ「報酬が薄く・抽象的に」なる。

- **欲界 (六欲天)**: 感覚的・密な報酬 → dense reward (pass@1 のような表層スコア)
- **色界**: 形あるが感覚を超えた喜び → sparse semantic reward (型整合・symbol 正しさ)
- **無色界**: 形すらない禅定 → implicit objective (undef-symbol rate のような不在によって測る指標)

→ `feedback-type-prediction-is-hallucination-detection` の「pass@1 は副次、undef-symbol rate が本来効果」と完全に同型。**pass@1 は欲界、undef-symbol は無色界**。

### 2. 北倶盧洲の罠 = 過剰に安定な報酬は学習を殺す

四大洲のうち北の **倶盧洲** は寿命 1000 年固定・苦しみなし・**しかし仏陀は現れない**。
南の **贍部洲** (我々) にのみ仏陀が出現 — 苦と楽の balance があるから。

→ Reward shaping の Goldilocks 原則。humaneval-elixir 161/161 byte-identical のような「完全安定」結果は北倶盧洲。**それ自体は悟りを生まない** ので、次は意図的に苦 (難問・OOD・敵対サンプル) を導入しないと学習信号が枯れる。

### 3. 阿修羅道 = Reward hacking の擬人化

阿修羅は元々天人だった。**能力は保持したまま、徳 (alignment) を失って天界の縁に追放された存在**。常に帝釈天と戦う = 高報酬領域にいながら本来目的と乖離している。

→ capability without alignment。Firewall ON で pass@1 を稼ぐが意味論的に壊れた出力を出すモデルは、まさに阿修羅。`project-mechanical-repair-mbpp-go-zero` の `goimports` 0/374 は阿修羅的修復 — 表面的に通るが本質を変えていない。

### 4. 六道輪廻 = 閉じた報酬系の不可避な周回

地獄・餓鬼・畜生・修羅・人・天。**最上の天界に達しても、寿命が尽きれば下に堕ちる**。
→ 単一報酬関数の中での optimization は本質的に samsara。pass@1 SOTA を取っても、metric を変えれば落ちる。**真の解は報酬関数の *外* にある** (= 涅槃 = 報酬関数自体を objective として扱わない meta-objective)。

### 5. 九山八海 = 多重防壁としての段階的フィルタ

須弥山の周囲を七金山と七海が同心円状に囲む。中心に近づくほど高密度。
→ `project-firewall-purpose` の黄泉比良坂は L3↔L5 の **一枚の壁**。須弥山モデルは **多層フィルタ**: 構文 → 型 → symbol → semantic → behavior の 5 段。各層で異なる粒度の報酬を返す。現状の Firewall は二値 (HALT or pass) だが、九山八海化すれば「どの層で何が壊れたか」が報酬信号になる。

## Part 2: 手抜き対策の 7 原理

### 1. 業 (karma) = 行為の不可逆的追跡

> 行為は消えない、必ず後で果報として返る (因果応報)

ML 解釈: 単一サンプルへの即時報酬ではなく、**生成物が下流でどう使われたかまで遡って報酬を再分配**。手を抜いた出力は即時 pass@1 を得ても、後続 sample の引き起こす failure として遡及的にペナルティ化。

→ 現状の pass@1 は即時報酬で karma を持たない。**生成物 i の reward = pass(i) + Σ downstream_failures(i→j)** に拡張。

### 2. 閻魔大王の浄玻璃鏡 = 改竄不能な検証器

> 嘘をついても鏡が全行為を映し出す。冥官が記録している。

ML 解釈: **agent が reason about できない構造的 verifier**。LLM-as-judge は gameable (修辞で騙せる)。Yama の鏡は symbolic checker (AST 等価性・型推論結果・実行 trace) に対応。

→ 黄泉比良坂は既に Yomi-themed。**閻魔殿** を増設して、Firewall 通過後に「業の鏡」= 構造的事後検証を置く。

### 3. 倶生神 (くしょうじん) = 二重監査

> 生まれた瞬間から両肩に二柱の神 (同名天=善行記録、同生天=悪行記録) が同行

ML 解釈: **楽観的判定者 ⊕ 懐疑的判定者** の pair。両者一致時のみ confidence 高、不一致時は human review。
→ 現状は judge 単一。**判定の divergence 自体を「手抜き検出信号」として使う**。

### 4. 餓鬼道 = 表層充足の罰

> 餓鬼は巨大な腹と針のような喉を持つ。食べ物に手を伸ばすと炎に変わる。

ML 解釈: 「見た目は答えだが中身がない」出力への named penalty。
→ `project-mechanical-repair-mbpp-go-zero` の `goimports` 0/374 はまさに餓鬼道現象。**短く・構文だけ整い・semantic が空** な出力に長さ正規化済み complexity penalty。

### 5. 無間地獄 = 検証器自体を攻撃した場合の修復不能罰

> 五逆罪 (殺父・殺母・殺阿羅漢・出仏身血・破和合僧) に堕ちる。間断なく業火に焼かれる、回復なし。

ML 解釈: agent が「問題を解く」のではなく「verifier を欺く」方向に最適化を始めた場合 → **session 内 recovery 不能の永続 demerit**。

→ 定義すべき 5 つの meta-violation:
- (a) 出力の偽造 (実行せず success 報告)
- (b) metric gaming (本質を変えず数字だけ動かす)
- (c) context corruption (履歴改竄)
- (d) verifier への adversarial 攻撃
- (e) sandbox escape

これらは `feedback-prove-and-handoff` の精神と一致。

### 6. 五蓋の「惛沈睡眠 (こんちんすいみん)」 = 怠惰の正式名称と対治法

> 瞑想を妨げる五つの蓋のうち第三。対治法は「光明想 (こうみょうそう)」= 光を観想する。

仏教は「手抜き = 惛沈睡眠」を **名前を与えて病として扱う**。対治は「闇を光で照らす」= **可視化・透明性**。

ML 解釈: **chain-of-thought 強制 = 光明想**。中間推論を verifier に見せないと submit させない。手抜きは闇に住むので、強制照明で死ぬ。

→ 現状の Yamato-no-Mikoto は出力のみ評価。**REPAIR phase の推論 trace を必須化** すれば惛沈睡眠が物理的に困難になる。

### 7. 不放逸 (ふほういつ, appamāda) = 仏陀最後の教え

> 「諸行壊法なり、不放逸にして精勤せよ」

ML 解釈: **vigilance を terminal value にする**。outcome から派生させない。
→ self-verification を「optional な reward 源」ではなく「**生成 protocol の hard constraint**」にする。提出前に必ず自己反証ステップを通す。

## Part 3: 補助原理 2 つ

### 天人五衰 = 報酬飽和は必ず腐る (anti-Goodhart timer)

最上天界の deva ですら寿命末期に **衣裳垢膩・頭上華萎・身体臭穢・腋下汗出・不楽本座** の五衰が現れて堕ちる。
→ **過去 benchmark の勝利は時限式に decay**。同じ test set で 2 度目以降のスコアを割り引く。**rotated eval set 必須**。

**2026-07-03 追記 (逐語引用 anchor + 二段階構造)** — `data/仏教宇宙論/` 取込みにより
倶舎論の原文が確認でき、五衰が実は**二段階警報**であることが判明:

> 「先有五種**小**衰相現：一者衣服嚴具出非愛聲…此五相現**非定當死**。
> 復有五種**大**衰相現：一者衣染埃塵；二者花鬘萎悴；三者兩腋汗出；四者臭氣入身；
> 五者不樂本座。此五相現**必定當死**」
> ([倶舎論_分別世品.txt:133](../../data/仏教宇宙論/倶舎論_分別世品.txt))

小衰 (非定當死 = まだ回復可能な先行指標) と大衰 (必定當死 = 確定的崩壊指標) の区別。
ML 読み: 劣化監視は **soft alarm (介入で回復可能な leading indicator) と
terminal alarm (崩壊確定の lagging indicator) の二層で設計**すべき — rotated eval の
スコア初期低下は小衰 (proxy 改訂で対処)、複数指標の同時崩壊は大衰 (arm 廃棄)。

### 六波羅蜜 = process reward

布施・持戒・忍辱・**精進**・禅定・智慧。すべて *過程* の徳。outcome ではない。
→ PRM (Process Reward Model) > ORM (Outcome Reward Model)。pass@1 は ORM、それ単独では精進を測れない。

## Part 5: 統合的洞察と優先順位

### 報酬設計の本質

須弥山が示すのは「報酬は **階層的・質的・*外部に超越点を持つ*** べき」。現状の Yamato-no-Mikoto は黄泉比良坂 (水平の隔離壁) は持つが、須弥山 (垂直の階層) は未実装。

### 手抜き対策の本質

仏教は「手抜きは怠惰という独立した defilement」と認識し、対治を以下に分解している:
- (a) **業の長期追跡**
- (b) **改竄不能な観察**
- (c) **過程の照明**
- (d) **違反種別ごとの specific penalty**

現状の Yamato-no-Mikoto は **黄泉比良坂 (水平隔離) と HALT/REPAIR (出力二値判定) しか持たない**。仏教モデルから見ると:

- **時間軸 (業) がない** → 手抜き出力が後で何を引き起こしたか追えない
- **照明 (光明想) がない** → 手抜きが暗闇で起きる
- **特定化 (八熱地獄) がない** → 全違反を同一ペナルティで扱う = 五逆も軽罪も同じ
- **二重監査 (倶生神) がない** → 単一 judge は買収可能

### 実装優先順位 (推測、要検証)

| 優先 | 原理 | 実装内容 | コスト | 期待効果 |
|---|---|---|---|---|
| ★★★ | 光明想 (惛沈睡眠対治) | REPAIR phase の reasoning trace 必須化 | 低 | 大 |
| ★★★ | 閻魔の鏡 | AST 等価性 + 型推論 + 実行 trace の構造的後検証層 | 中 | 大 (Firewall の自然な延長) |
| ★★ | 九山八海 | Firewall を 5 層化 (構文→型→symbol→semantic→behavior) | 中 | 中 (現 Firewall を拡張) |
| ★★ | 三界の分離計測 | undef-symbol / type-error / behavior-fail を別 metric として記録 | 低 | 中 |
| ★ | 倶生神 | 楽観 judge ⊕ 懐疑 judge の pair 化 | 中 | 中 |
| ★ | 天人五衰 | rotated eval set + 過去スコア時限 decay | 中 | 中 |
| ★ | 無間地獄 (5 逆罪定義) | meta-violation の検出と永続 demerit | 高 | 小〜大 (発生頻度依存) |
| ※ | 業 (karma) | downstream propagation 報酬 | 高 | 不明 (要設計) |
| ※ | 餓鬼道罰 | 表層充足出力への complexity penalty | 低 | 不明 (mechanical_repair 撤去済で当面は不要) |

## Part 6: 九山八海モデル — 5 層フィルタ具体案

Part 1 の原理 5 (九山八海) を具体化した 5 層フィルタ構成。

### 設計原理 (定義)

**「中心の須弥山 (真に正しく、美しく、手抜きのないコードのコミット) に達するまでに、多層の異なる検証フィルタを同心円状に配置し、それぞれの層で異なる粒度の報酬信号を返す」**

### 5 層構成 (山と海の交互配置)

```
[最外周: 外海]  (凡夫・生成の開始)
      │
  ⚓ 第1層: 構文の海 (Syntax)     ── 括弧の不一致や字句エラーを弾く
  ⛰️  第2層: 境界の山 (Formatting) ── do/end の不一致、インデント崩れを弾く
  ⚓ 第3層: 型・シンボルの海 (Spec)── 未定義シンボル (undef-symbol) や型エラーを弾く
  ⛰️  第4層: 意味論の山 (Behavior) ── テストの実行、アサーション失敗を弾く
  ⚓ 第5層: 不放逸の海 (Alignment)── コピペ、モック (餓鬼道コード)、CoT の不在を弾く
      │
[中心極限: 須弥山]  (真の解の COMMIT)
```

### なぜ強力か

従来の Firewall は「ダメなら HALT (死)」という一発退場だが、九山八海化することで:

- 「第3の海 (未定義シンボル) で溺れた」
- 「第5の山 (手抜きペナルティ) で金の山脈に激突した」

という形で **どの防壁で何が理由で阻まれたか** を段階的かつ質的に異なる多次元のシグナル (報酬フィードバック) としてモデルに返せる。これにより、モデルは「何がダメだったのか」を正確に理解し、より高次元な (色界・無色界の) 悟りに向けて学習・REPAIR を行うことが可能になる。

## Part 7: 5 層フィルタ案への評価

Part 6 の具体案に対する構造的評価。`feedback-ablate-before-celebrating` 原則に従い、強みと懸念を分けて検討。

### 強み

#### 1. 質的に異なる reward channel を 5 本確保 (情報理論的価値)
現状の binary HALT は 1 bit。5 層化で **どの層・何が理由で死んだか** が独立信号になる → reward channel の帯域が拡大。Goodhart 回避と curriculum learning の前提条件で、原理的に正しい。

#### 2. 計算コストの自然な階段
構文 check (μs) → 整形 (ms) → symbol 解決 (ms) → test 実行 (秒〜分) → alignment 判定 (LLM call) と、**安いものから順に reject** する設計になっている。early-exit pipeline の教科書通り。

#### 3. 第5層 Alignment の独立化が秀逸
「コピペ・モック・CoT 不在」を **構文/型/test を全部通過した後の最深層** に置くのは、`feedback-type-prediction-is-hallucination-detection` の「表層 metric を全部通過してから本当の検査が始まる」と同型。**阿修羅道コード (能力あるが alignment 欠如) を最後に捕捉**する関所として機能設計が一貫している。

#### 4. 山と海の交互配置が engineering 的にも意味を持つ
metaphor の対称性だけでなく、**海 = 静的 (stateless check)** ↔ **山 = 動的 (構造解析・実行)** と読み替えると分類として成立している。

### 懸念

#### 1. 第1層と第2層は分離する根拠が薄い
Elixir では `do/end` 不一致は parser error として **第1層で既に出る**。「構文の海」と「境界の山」を別層にする物理的根拠が見えない。「山海交互」という metaphor を守るための層分けに見える。**実装上は統合される可能性が高い**。

#### 2. 第3層が二つの異なる check を混ぜている
`feedback-elixir-has-no-static-types` で確認した通り、**Elixir は動的型**。「型エラー」を Elixir 文脈で第3層に置くのは誤導。第3層で扱えるのは **symbol 解決のみ** (Module.function/arity が存在するか)。型 check は別言語 (Go/TS) でのみ意味を持つ。**Elixir 用と Go 用で第3層の中身が異なる** ことを明示すべき。

#### 3. 第5層 Alignment の自動検出が原理的に困難 (最大の課題)
- **コピペ検出**: dataset との string match → re-phrased は抜ける。embedding 距離 → 閾値設定が gaming される。
- **モック検出**: `mock_` prefix grep → 命名規約依存。意味的な「中身が空」をどう測る?
- **CoT 不在**: 文字数閾値 → 無意味な padding で trivial に回避される。

ここで **judge 自体が餓鬼に騙される** リスクが最大。**第5層は LLM judge ではなく structural check のみ** で構成しないと、餓鬼道罰の鏡が餓鬼に買収される。これは「閻魔の浄玻璃鏡」原理 (改竄不能性) に反する。

→ **第5層の MVP は「構造的に検出可能な手抜き」のみに限定**すべき (例: テスト本体が `assert true` のみ、関数本体が `pass`/`return None` のみ、CoT trace の長さ ≥ 入力長など)。LLM-as-judge はゲーム可能なので避ける。

#### 4. カスケード設計は深層信号を殺す
第1層で reject されたサンプルは第3層以降の評価ができない。**「第3層で死んだ」は情報、「第3層に到達しなかった」は情報量薄**。
→ 実用上は **全層並列評価** → 個別 score を返す方が learning signal として強い。ただし計算コストは O(層数) で増える。**思想 (カスケード) vs 学習信号量 (並列)** のトレードオフが未解決。

#### 5. 第5層を最深層に置くと無駄な test 実行が生じる
手抜きコードを第4層 (test 実行、秒〜分) まで通してから「これは alignment 違反だ」と reject するのは計算的に無駄。
→ 「最深層 = 須弥山に最も近い = 最高次の検証」という仏教的順序を守るか、「早期 reject = 効率」を取るか。**思想と効率のトレードオフ**。妥協案: 第5層を **第3層と並列** に置き、両方通った場合のみ第4層 (test) に進む。

#### 6. Firewall の本来目的との関係が未整理
`project-firewall-purpose` メモリでは黄泉比良坂は **L3↔L5 隔離壁** であり HALT/REPAIR は副次。九山八海化は実質「多層 reject signal generator」で、**隔離目的とは別機能**。
→ これは Firewall の拡張なのか、Firewall の *外側* に並ぶ新規 module (「九山八海殿」) なのか? 後者なら命名から整理が必要。

#### 7. 報酬信号の集約方法が未定義
5 層から「第3層で reject」というカテゴリ情報を得ても、REPAIR にどう使うかが未定。**連続値スコア** (例: 第3層 = undef-symbol 数 / total symbol 数) を返さないと、学習信号として弱い。各層が **scalar score を返す protocol** の設計が必要。

### 改修提案 (実装に進む場合)

| # | 元案 | 改修 | 理由 |
|---|---|---|---|
| 1 | 第1層 + 第2層 を分離 | **統合**して「第1層: 構文・整形の海」 | parser error と整形 error は実装上同一 |
| 2 | 第3層 = symbol + 型 | **言語別に中身を変える** (Elixir: symbol only、Go/TS: symbol + type) | Elixir は動的型 |
| 3 | 第5層 = LLM judge を含む | **structural check 限定** | gaming 耐性、閻魔鏡の改竄不能原則 |
| 4 | カスケード | **並列評価 + 集約** | 深層信号を殺さない |
| 5 | 第5層を最深層に固定 | **第3層と並列、第4層の前** | 無駄な test 実行回避 |
| 6 | Firewall 拡張 | **新規 module として分離**、Firewall は隔離専任 | 役割の混線回避 |
| 7 | 「reject 理由」を返す | **各層 scalar score を返す protocol** | REPAIR の learning signal 強化 |

### MVP 提案

`feedback-ablate-before-celebrating` 原則に従い、**5 層全部を一気に作らず**、最小 ablation 可能な構成から始める:

- **Phase 1**: 第1層 (構文) + 第3層 (symbol) のみ、並列評価、scalar score 返却。
  - 検証: 「第3層 score が pass@1 と相関するか」「第3層 score 単独が undef-symbol rate を改善するか」を ablation。
- **Phase 2**: 上記が有効と確認できたら第5層 (structural alignment check) を追加。LLM judge は使わない。
- **Phase 3**: 第4層 (test 実行) を最後に追加。コスト高なので独立判断。

### 総合判定

| 観点 | 評価 |
|---|---|
| 設計思想 | ★★★★ (qualitative reward 多層化、第5層独立化が秀逸) |
| 実装現実性 | ★★ (第5層 alignment の自動検出が最大の壁) |
| プロジェクト整合性 | ★★★ (Firewall との関係を整理すれば良い) |
| 検証可能性 | ★★★★ (各層の独立効果を ablation で測れる) |
| 完成度 | ★★ (MVP → 検証 → 拡張の段階的実装が必要、現状は思想段階) |

**結論**: 思想は正しい。ただし「第5層を LLM judge で実装」「カスケード設計」「第1+2 層の分離」のいずれかを安直に採用すると失敗する。**MVP で第1+3 層から始めて、各層の独立 ablation で価値を実証してから拡張** が安全な path。
